# Excel 转换器两种修复方案对比

## 1. 背景

项目使用 Univer 0.22 作为表格引擎，通过 `xlsxConverter` 完成 `.xlsx` 与 Univer `IWorkbookData` 之间的转换。

本次针对表格粘贴和保存问题实现了两个独立分支：

| 分支 | 方案 | 提交 |
|---|---|---|
| `codex/replace-luckyexcel` | 将转换依赖替换为 `@zwight/luckyexcel` | `f27952e` |
| `old` | 保留 `@mertdeveci55/univer-import-export`，修复粘贴样式导出错误 | `2d05ec3` |

两种方案都继续使用现有的 `XlsxConverter` 抽象，未修改 `fileStore`、文件接口和组件调用链。

## 2. `codex/replace-luckyexcel` 分支修改

### 2.1 依赖调整

修改 `frontend/package.json` 和 `frontend/package-lock.json`：

- 删除 `@mertdeveci55/univer-import-export@^0.2.1`。
- 添加 `@zwight/luckyexcel@^1.1.6`。
- 删除显式安装的 `xlsx@^0.18.5`。新依赖使用 `@zwight/exceljs`，不再需要原转换包运行时依赖的 SheetJS。

### 2.2 转换器切换

修改 `frontend/src/utils/xlsxConverter.luckyexcel.ts`：

- 将默认导入切换为 `@zwight/luckyexcel`。
- 保持 `toUniver(blob, fileName)` 和 `toXlsx(snapshot, fileName)` 接口不变。
- 调用方不需要感知底层依赖已经替换。

### 2.3 导出缓冲兼容

`@zwight/luckyexcel` 导出时可能返回以下任一类型：

- `ArrayBuffer`
- `Buffer`
- `Uint8Array` 或其他 `ArrayBufferView`

转换器新增 `toArrayBuffer()`，根据 `byteOffset` 和 `byteLength` 截取准确的数据区间，再构造 `.xlsx` Blob，避免 Node 风格 Buffer 的底层共享缓冲区产生多余字节。

### 2.4 公式导出兼容

测试发现 `@zwight/luckyexcel@1.1.6` 导出器错误地从 `cell.si` 读取公式内容，而 Univer 0.22 的标准公式字段是 `cell.f`。

如果直接替换依赖，公式会被错误写入数字格式字段，保存后的 Excel 公式丢失。

转换器新增 `adaptSnapshotForExport()`：

- 只遍历有数据的单元格。
- 只对存在 `cell.f` 的公式单元格创建副本。
- 导出副本中将公式文本写入该依赖实际读取的 `cell.si`。
- 清除副本中的 `cell.f`，防止公式被误当成数字格式。
- 不修改 Univer 提供的原始工作簿快照。
- 使用行、工作表、工作簿逐层 copy-on-write，避免深拷贝整个工作簿。

### 2.5 测试调整

修改 `frontend/tests/xlsxConverter.spec.ts`：

- 测试样本改为直接读取 `frontend/public/fixtures`，解决 Windows 下 `tests/fixtures` 软链接不可用的问题。
- 保留 6 个样本的导入、导出、重新导入测试。
- 兼容 LuckyExcel 将普通文本转换为 Univer 富文本 `p.body.dataStream` 的表示差异。
- 忽略二次解析时自动增加的 `General` 数字格式和默认文本类型标记。
- 继续比较工作表名称、合并单元格、值、公式和非默认样式。
- 增加 `large-10k-rows.xlsx` 解析性能测试，要求解析耗时低于 5 秒。

### 2.6 文档调整

- 更新 `CLAUDE.md` 中的依赖说明、公式兼容问题和缓冲类型说明。
- 更新设计文档中的 LuckyExcel 依赖选择。

### 2.7 验证结果

- 全量测试：20 个测试全部通过。
- TypeScript 类型检查通过。
- Vite 生产构建通过。
- 1 万行样本单次解析实测约 421 ms。
- 生产主 JavaScript 包约 9,430 KB，gzip 后约 2,582 KB。

## 3. `old` 分支修改

### 3.1 保留原依赖

生产依赖继续使用：

```text
@mertdeveci55/univer-import-export@^0.2.1
xlsx@^0.18.5
```

没有替换转换器，也没有引入另一套嵌套 Univer 运行时。

测试代码显式增加 `@zwight/exceljs@4.4.2` 开发依赖，用来读取生成的 `.xlsx` 并断言真实字体属性。该包本来就是原转换器的传递依赖，增加开发依赖不会改变生产转换路径。

### 3.2 问题根因

粘贴整行后，Univer 可能生成如下关闭状态样式：

```ts
{
  bl: 0,
  it: 0,
  ul: { s: 0 },
  st: { s: 0 },
}
```

其中：

- `ul.s === 0` 表示未启用下划线。
- `st.s === 0` 表示未启用删除线。

原依赖导出器使用类似以下逻辑：

```ts
underline: !!style.ul
strike: !!style.st
```

虽然 `s` 为 0，但 `{ s: 0 }` 是一个对象，转换为布尔值后仍然是 `true`。因此保存时，关闭状态被错误写入 Excel 为启用状态。

### 3.3 导出前样式清理

修改 `frontend/src/utils/xlsxConverter.luckyexcel.ts`，新增导出快照清理逻辑：

- `stripDisabledTextDecorations()` 只删除 `ul.s === 0` 和 `st.s === 0` 的字段。
- `ul.s === 1` 和 `st.s === 1` 保持不变，真实启用的下划线和删除线不会丢失。
- 清理工作簿 `styles` 样式表，覆盖通过样式 ID 引用的粘贴样式。
- 清理单元格内联样式。
- 清理富文本 `textRuns[].ts` 中的文本装饰样式。
- 清理工作簿默认样式。
- 使用 copy-on-write；没有问题的样式、单元格、行和工作表继续复用原对象。
- 原始 Univer 快照不会被修改。

清理后的快照只用于调用 `transformUniverToExcel()`，导入流程完全不变。

### 3.4 回归测试

新增粘贴样式保存测试：

- 构造通过工作簿样式 ID 引用的 `{ul:{s:0}, st:{s:0}}` 单元格。
- 构造真实启用 `{ul:{s:1}, st:{s:1}}` 的对照单元格。
- 导出为 `.xlsx`。
- 使用 ExcelJS 直接读取保存文件中的字体属性。
- 断言关闭状态没有产生下划线和删除线。
- 断言真实开启状态仍然存在。

同时修复 Windows 下测试样本路径问题。

### 3.5 验证结果

- 全量测试：20 个测试全部通过。
- TypeScript 类型检查通过。
- Vite 生产构建通过。
- 1 万行样本完成“导入、导出、重新导入”实测约 1,097 ms。
- 生产主 JavaScript 包约 9,653 KB，gzip 后约 2,623 KB。

## 4. 两种方案对比

| 对比项 | `codex/replace-luckyexcel` | `old` |
|---|---|---|
| 核心思路 | 替换整个转换依赖 | 保留原依赖，修复明确缺陷 |
| 修改范围 | 依赖树、锁文件、转换器、公式适配、测试语义 | 转换器导出前样式清理、回归测试 |
| Univer 兼容方式 | 新包内部声明 `@univerjs/core@^0.6.0`，与项目 0.22 并存 | 原包使用 `@univerjs/core >=0.6.0` peer dependency，复用项目版本 |
| 公式处理 | 必须把 `cell.f` 适配到依赖错误读取的 `cell.si` | 使用原包对 `cell.f` 的支持，无额外公式字段适配 |
| 粘贴样式问题 | 通过更换实现绕开原问题 | 直接修复 `{s:0}` 被当成启用的根因 |
| 原始快照 | 公式单元格 copy-on-write | 问题样式 copy-on-write |
| 解析性能 | 1 万行单次解析约 421 ms | 1 万行完整 round-trip 约 1,097 ms；不是同一测量口径，不能直接计算性能差值 |
| 构建体积 | 主包约 9,430 KB | 主包约 9,653 KB |
| 回归风险 | 较高，转换实现和内部数据表示均发生变化 | 较低，只处理两个明确错误字段 |
| 维护风险 | 需要长期维护公式和 Univer 版本兼容层 | 需要保留导出前样式清理层 |
| 锁文件变化 | 较大，替换依赖及传递依赖 | 很小，仅增加测试直接依赖声明 |

## 5. `codex/replace-luckyexcel` 的优缺点

### 优点

- 满足“直接替换依赖”的要求。
- 1 万行解析测试表现良好。
- 不再需要显式安装 `xlsx`。
- 当前构建产物比 `old` 分支小约 223 KB，gzip 后小约 41 KB。
- 6 类 Excel 样本 round-trip 和公式测试均已通过。

### 缺点

- `@zwight/luckyexcel` 声明并安装了 `@univerjs/core@0.6.x`，项目本身使用 0.22，存在两套核心版本。
- 即使当前只交换普通快照，没有注册旧运行时，重复核心依赖仍增加依赖冲突和后续升级风险。
- 1.1.6 的公式导出实现与 Univer 标准字段不一致，必须长期维护 `cell.f -> cell.si` 兼容层。
- 二次解析会把部分普通文本转换为富文本结构，并增加默认样式字段，内部数据表示变化更大。
- 依赖替换导致锁文件和传递依赖变化较多，真实业务文件需要更广泛的视觉回归。
- 新包未来升级后，如果修复了 `si` 错误，现有适配层也需要同步调整，否则可能产生双重处理。

## 6. `old` 的优缺点

### 优点

- 直接针对粘贴保存出现下划线和删除线的根因修复。
- 不改变当前已经验证过的 Excel 导入、导出实现。
- 原包通过 peer dependency 使用项目现有 Univer 版本，依赖结构更一致。
- 不需要修改公式数据结构。
- copy-on-write 只在发现明确关闭的装饰字段时复制对象。
- 回归测试直接检查最终 `.xlsx` 字体属性，验证的是用户实际打开文件时看到的结果。
- 改动范围较小，回归风险和部署风险更低。
- 将来原依赖修复该问题时，可以删除清理函数和对应兼容说明，迁移成本较低。

### 缺点

- 仍然依赖存在该缺陷的第三方包，修复逻辑由项目自行维护。
- 导出前需要遍历已使用的单元格和样式，理论上增加一次 O(n) 扫描。不过 Excel 导出本身也必须遍历相同数据，实际影响通常较小。
- 继续保留显式 `xlsx` 依赖。
- 构建产物比替换方案略大。
- 原依赖运行时输出较多调试日志，后续可以单独评估是否需要上游修复或构建时移除。

## 7. 允许升级 Univer 时的分析

### 7.1 升级 Univer 不会自动消除转换风险

该项目当前使用 Univer 0.22。升级 Univer 可以获得后续的 bug fix、性能优化和更新的快照结构，但同时会改变 `.xlsx` 转换器需要适配的数据契约。

升级时需要重新验证的范围不只是 `IWorkbookData`，还包括：

- `ICellData` 公式、富文本和样式字段语义。
- Univer 插件注册顺序和依赖注入 token。
- Facade API、编辑事件和 dirty state 监听。
- 各插件语言包路径和资源结构。
- 公式、条件格式、数据验证、图片和过滤器的快照资源格式。

因此，“允许升级 Univer”并不等于“可以忽略转换器的版本对齐”，恰好相反：转换器必须更严格地与目标 Univer 版本对齐。

### 7.2 升级后两个候选依赖的差异

#### `@zwight/luckyexcel`

`@zwight/luckyexcel@1.1.6` 在生产依赖中直接声明 `@univerjs/core@^0.6.0`。当应用升级到比 0.22 更新的 Univer 时，应用与转换器内的快照模型距离只会更大。

即使当前没有将它内嵌的 Univer 注册进应用容器，仍然存在：

- 两套 Univer core 依赖。
- 旧快照字段语义与新版不一致。
- 公式字段 `f` / `si` 的已知错误适配。
- 每次 Univer 升级后都需要重新审计整个数据映射层。

所以，Univer 版本越新，该方案的长期风险越高。除非同时 fork 该包，将 Univer 改为受控的 peer dependency 并修复公式导出，否则不建议把它作为升级后的长期基础。

#### `@mertdeveci55/univer-import-export`

`@mertdeveci55/univer-import-export@0.2.1` 将 `@univerjs/core` 声明为 `>=0.6.0` peer dependency，会复用应用选定的 Univer 版本。这种依赖形式更适合升级。

但 `>=0.6.0` 的范围过宽，只代表 npm 允许安装，不代表所有新版 Univer 都经过了行为验证。升级后仍需要：

- 用目标 Univer 版本运行全部 round-trip 样本。
- 对比升级前后的快照 schema。
- 使用 Excel/WPS 检查真实业务文件。
- 将 peer dependency 范围收紧到项目实际验证过的 Univer 主版本。

与 `@zwight/luckyexcel` 相比，它是更合适的升级过渡基础，但不应把宽泛的 peer dependency 当作完整的兼容承诺。

### 7.3 允许升级时的最优方案层级

如果不限定必须从两个现有分支中二选一，推荐顺序如下：

1. **与目标 Univer 版本完全对齐的官方 `.xlsx` 转换能力。** 如果目标版本提供了可接受的官方导入导出方案，并且商业许可和部署方式符合项目约束，这是长期最优解。快照 schema 和转换器由同一团队维护，版本错配风险最低。
2. **基于 `@mertdeveci55/univer-import-export` 维护项目级 fork。** 如果必须保持完全开源和前端离线转换，应将当前 `{s:0}` 修复下沉到 fork，删除调试日志，收紧 peer dependency，并针对目标 Univer 版本持续运行样本矩阵。这是完全开源约束下的长期最优解。
3. **使用 `old` 分支的项目边界适配。** 这是当前可立即落地、风险最低的方案，也是未来创建项目级 fork 的正确起点。
4. **直接使用 `@zwight/luckyexcel@1.1.6`。** 只适合当作短期实验或备用路线，不建议作为新版 Univer 的长期转换层。

### 7.4 升级路线建议

| 阶段 | 建议 |
|---|---|
| 当前修复 | 合并 `old` 分支，先解决已确认的粘贴样式错误 |
| Univer 升级 PoC | 单独建立升级分支，不同时更换转换器，先让现有样本矩阵通过 |
| 转换层收敛 | 评估目标 Univer 版本的官方方案；不适用时，fork `@mertdeveci55/univer-import-export` |
| 长期维护 | 锁定已验证的 Univer 版本范围，每次升级必跑真实文件和视觉回归 |

不建议在一个变更中同时完成“Univer 跨版本升级”和“LuckyExcel 实现替换”。两个变量同时改变后，公式、样式或资源丢失时很难快速定位责任边界。

## 8. 推荐方案

在当前项目和当前问题范围内，推荐采用 `old` 分支方案。在允许升级 Univer 的前提下，`old` 仍是更好的迁移起点，但长期目标应转为与目标 Univer 版本严格对齐的官方转换器或项目级 fork。

主要原因如下：

1. **它修复的是已确认的根因。** 问题不是 Univer 粘贴本身，也不是整个 Excel 转换器不可用，而是导出器错误地把 `{s:0}` 对象按真值判断。删除明确关闭的字段即可恢复正确行为。
2. **修改范围更小。** 不替换核心转换实现，不改变依赖树，不改变公式格式，也不改变普通文本的内部表示。
3. **与 Univer 0.22 的依赖关系更合理。** 原包使用 peer dependency；替换包会额外安装 Univer 0.6.x。
4. **避免引入新的已知缺陷。** 替换方案必须额外修复公式字段读取错误，这说明替换依赖并没有减少兼容代码，只是把兼容问题从样式转移到了公式和版本管理。
5. **验证更贴近用户场景。** `old` 分支测试直接读取最终 Excel 文件的字体属性，能够确认保存文件中没有错误的下划线和删除线。
6. **更容易回退和维护。** 清理逻辑集中在 `xlsxConverter` 边界，将来可以单独删除、替换或提交给上游，不影响文件存储和 UI。

## 9. 建议的后续处理

- 当前生产合并优先选择 `old` 分支。
- 使用至少 3 份真实业务文件执行“粘贴整行、保存、刷新、下载后用 Excel/WPS 打开”的人工验证。
- 将 `{s:0}` 布尔判断问题反馈给 `@mertdeveci55/univer-import-export` 上游。
- 如果未来继续考虑 `@zwight/luckyexcel`，至少应等待或自行解决以下问题：
  - 将 `@univerjs/core` 改为兼容项目版本的 peer dependency。
  - 修复公式导出读取 `cell.si` 的问题。
  - 增加真实业务文件的视觉回归测试。
  - 对比首开性能、解析性能、导出性能和内存峰值，而不只比较单次解析时间。

最终建议不是永久绑定原依赖，而是在当前证据下选择风险最低、最直接且最容易验证的修复路径。
